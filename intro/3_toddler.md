# 幼儿期

这个阶段定义为幼儿期，是因为发生了一件标志性的事件：我们第一次显性地做了领域边界的重划。把需求、意图、规格、实现这套模型，连同六篇形式化正课，整体从元工程移到了软件工程领域（quanttide-code）。之前所有的内容都在元工程这一个领域里长，边界是隐性的——凡是在代码之前的，都算元工程的。这是第一次说"这个不是我的"，用减法给自己下定义。

划完之后，元工程的定位反而清楚了。以前它是"软件工程的前一阶段"，和需求分析抢活；现在它是工程时间线之外的判断层。

追记原因的话，直接原因是一次概念上的分开：我们用「范畴」专指康德式的古典范畴，用「范式」指数学范畴论的结构——对象、态射、交换图那一套。孕育期以数学范畴论为中心做实验效果不好，根子就是拿范式去做范畴的活，过度抽象；给两个词分了名，那个错误才真正解开。这次迁移的边界也是被这条线划的：走的是范式，留的是范畴。四层与六篇正课——集合、逻辑、状态机、细化、交换图——全是范式一侧的活，所以整体去了软件工程；创始人的第二大脑孵化元模块时做的分类、今天档案更新里做的分类与具体第二大脑 AGENTS 文件对应的元认知显性化，都是范畴一侧的活，留在元工程。

范畴留下的实际收益，是跨领域迁移能力明显增强了：一个领域的新思路可以快速迁到另一个领域，因为各域在范畴这一层基本同构。今天的档案编辑历史就是实证——客户支持域立起「工单→工作日志」的核心循环后，「记录段落 journal 范畴、加工整理段落 profile 范畴」的两段结构原样迁到智能体域，变成「对话→harness 日志」；支持、智能体、咨询、设计四个域一天之内走的都是同一套七格冷启动。同构，所以迁移是替换式的，思路沿骨架传播，不用每个域重新发明。

这条迁移里真正被搬走的判断是：不把原始记录当成交付，交付的是加工以后的记录。原始记录只是证据，加工层才具备控制质量的可能；同一件事重复处理出来的记录，不如处理新情况产出的记录有价值——新情况才迫使人立新范畴、扩骨架，重复处理只是在已有骨架上刷量。这也是档案仓把体裁收成元认知快照、四阶段流程可以整个移走而不伤筋骨的底气：证据层只增不改，留下的加工层才是资产。分开的标准是：四阶段是有次序、有验收、有退回的流程，有流程的东西属于工程——哪怕它形式化到要用 Lean 验证、要写不变量，它仍然是软件工程的事；元工程留下的是没有阶段的东西——问题是不是真问题、范畴立得对不对、系统里到底有什么存在。

拿这次迁走的内容走一遍就看得见分界。"退过款的支付单不能再退"怎么摊成需求、写成状态机、证不变量，这条走法现在归软件工程教程；但"退款算一个状态还是一个动作"这个归位判断，依据的方法——存在清单、范畴划分、边界测试——教它的章程还在元工程手里。流程在时间里一步步走，判断在任何一步都可能被叫停重裁。以前四阶段和六步混在一个仓里，看不出谁消费谁；分完之后依赖方向显形了：软件工程的意图阶段走到"归位"那一步，要回头找元工程要本体坐标。

由此得到一条以后可用的判据：一件事该不该留在元工程，只问它是不是流程开动之前或之中随时要做的判断。是，就留；不是——哪怕形式化程度再高、再像"元"的活——就走。`meta-align` 那条"范畴不许在领域侧增删，须回元工程层决策"，其实就是这个定位早就存在的执法，这次分离把一条零散的规则变成了整个领域的形状。

代价也要记下来：定位明确之后，元工程不能再拿"方法论工作流"当产出，它的产出只剩一种——供各领域流程消费的判断。如果存在清单和范畴裁定不再被软件工程的意图阶段回头引用，判断层就退化成书架。所以这次分离真正的后续考题在软件工程那边：意图阶段什么时候回头找元工程要本体坐标，这条回路越勤，分离越成立。
